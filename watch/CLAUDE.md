# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Companion-watch firmware for a LilyGo T-Watch Ultra (915MHz variant): a sailing display + remote control for the Moana boat unit — see issues #133/#138. A four-tile carousel — a **ring**, Speed ⇄ Mode ⇄ Control ⇄ Stats ⇄ Speed — shows SOG from the CoreS3's 1Hz ESP-NOW telemetry (Speed, the boot tile), sets any of the server's ten sailing modes (Mode, one left swipe away, issue #146), controls the boat's track recording with hold-to-confirm + state echo (Control), and shows live session/leg statistics with auto-cut on mode change (Stats, one right swipe from Speed the other way round the ring, issue #142), under a floating SD/link/battery header (the clock rides on the Speed tile, not the header). Built with PlatformIO + Arduino framework + [LilyGoLib](https://github.com/Xinyuan-LilyGO/LilyGoLib) (LVGL 9 UI). The broader subsystem-scoping firmware (tabview, buttons/haptics, GNSS, audio) lives on the `watch-scoping-firmware` branch.

## Build & Flash Commands

```bash
pio run                       # build
pio run --target upload       # flash
pio device monitor            # serial monitor (115200)
```

Or from the repo root: `mise run watch:build` / `watch:flash` / `watch:monitor`.

### If upload fails / USB port keeps disappearing

Put the watch into download mode manually:

1. Connect USB-C
2. Hold **BOOT**, tap **RST**, release **BOOT**
3. Upload; tap **RST** afterwards to reboot

## Toolchain notes (important)

- The environment mirrors [LilyGoLib-PlatformIO](https://github.com/Xinyuan-LilyGO/LilyGoLib-PlatformIO) — the only supported PlatformIO route for LilyGoLib. `boards/lilygo-t-watch-ultra.json` and `variants/lilygo_twatch_ultra/pins_arduino.h` are copied verbatim from it. Don't upgrade `platform` or dependency pins without checking that repo first.
- Every `lib_deps` entry is pinned to an exact version or commit — deliberately, no caret ranges. LilyGoLib in particular is pinned to `2eadcf7` because its `master` moved to IDF 6 display APIs that don't compile against IDF 4.4. If you need a newer dependency, bump the pin explicitly and re-verify the build; don't loosen it back to a range.
- The ESP-NOW wire format lives in `../shared/espnow_protocol.h`, shared with `device/`. Change it only in lockstep with the boat unit and bump `kProtocolVersion`.

## Architecture

Single-threaded Arduino loop (LVGL is not thread-safe): `instance.loop()` dispatches LilyGoLib device events, `lv_timer_handler()` drives the UI. The LVGL loop is the scheduler — one 250ms timer in `ui.cpp` builds an immutable `AppModel` snapshot per tick and hands it to the header + active tile; do NOT port the device's FreeRTOS event-queue architecture here. The one task off the loop is `buzzer`'s, which owns a blocking I2S write and touches no UI, model or I2C state. ESP-NOW receive lands on the WiFi task and is handed over via a spinlock-guarded struct in `espnow_link.cpp`.

- `src/main.cpp` — init + loop; caps the CPU at 80MHz and powers off the watch GNSS (speed comes from the boat only) for battery life
- `src/ui.cpp` — composition root: tileview carousel (columns Speed | Mode | Control | Stats, wrapped into a ring — LVGL's tileview is a flat strip, so `onEdgeGesture` turns the end tiles' dead-end swipe into a jump to the far end), the per-tick AppModel build, command-channel + stats-engine wiring, and the PWR-click manual leg cut (re-asserts the current echoed mode through the event queue; error buzz when not recording or mode unknown)
- `src/app_model.h` — the per-tick snapshot (telemetry, link age/state, recording echo, command status, stats-engine view); screens are dumb renderers of it. Pure header.
- `src/header.cpp` — floating header built once on `lv_layer_top()`: one row of status — SD-card icon (grey idle / white recording, canvas-drawn), signal-arcs link icon (white / amber >3s / grey+red slash >10s, **amber+slash** on a protocol mismatch), battery % — spaced evenly across the top, ending around y=42, plus a second line naming both protocol versions that exists only while a mismatch is live (issue #173: amber says frames are arriving, the slash says none of them are readable, and the numbers say which end needs reflashing). **No clock**: it was a header line on every tile through issue #159 and now belongs to the Speed tile alone. The two top-anchored tiles (`stats_screen`'s `kCardTop`, `mode_screen`'s `kListTop`) followed it up from y=100 to y=60 — move the icon row and they need checking again
- `src/speed_screen.cpp` — local time at the top in `font_time_56` (`kClockTop`), read from `timebase` and offset by `nz_time::utcOffsetSeconds` rather than from the packet in hand — since #144 the clock survives the boat being off, and `--:--` means the watch's own clock has never been set, not that the link is down. SOG digits (`font_speed_170`) centred — white while recording, amber while the boat is live but not recording (issue #184), greyed when link lost — then the mode chip on its own centred line (reading `NOT RECORDING` instead of a mode while the echo says idle) and a secondary session value under it (vertical swipe cycles 10s → MAX → AVG → off). The clock sits on this tile rather than in the header because Speed is the one screen with a free top band, and reading the time is part of the same tiller glance as reading the speed; it hangs well below the icon row, where as a header line it looked crammed. The mode/value pair were one row until issue #159, where a nine-letter mode name ran into the value beside it
- `src/mode_screen.cpp` — Mode tile (issue #146): one scrollable 64px row per `Mode.MODE_CHOICES` value, echoed mode filled, a queued-but-unacked tap outlined. Row labels, the sidecar's mode names and the server's `MODE_CHOICES` are one vocabulary — `moana::sailingModeName()` in `shared/espnow_protocol.h`; adding a mode means touching that function, the `SailingMode` enum, `events_jsonl.MODE_KINDS` and the model's choices together
- `src/stats_screen.cpp` — Stats tile (issue #142): current leg (LEG n + mode + time), DIST/AVG/MAX/10s grid, pinned session line (hold 1s to reset mid-session); vertical scroll browses past legs. The browse is dropped whenever the carousel lands on the tile (`onShown()`, off the tileview's `LV_EVENT_VALUE_CHANGED` in ui.cpp) — a pin left behind from last time could be many cuts back by now
- `src/stats_engine.cpp` — pure session/leg statistics (no Arduino/LVGL/radio): gate (fix, hdop, impossible-acceleration) → median-of-5 → per-leg/session MAX + best rolling 10s; distance purely from the boat's `cumulative_distance_m` echo (never watch-side haversine); legs cut on echoed mode change, same-mode re-asserts detected as the ack frontier advancing with an unchanged mode. A cut landing less than `kMinLegMs` after the leg opened *relabels* that leg instead — a leg that short is a mis-press just corrected (issue #161), and the server collapses the same burst on import from the same duration (`MODE_DEBOUNCE_SECONDS`, see the root `CLAUDE.md`). Debouncing retroactively rather than holding the press is deliberate: a hold would silence the haptic and the mode chip for 20s and the boat's sidecar would carry the mis-press anyway. Unit-tested in `test/test_native/`.
- `src/control_screen.cpp` — recording control per docs/watch-screen-mockups.html: echo-driven state label, hold-to-confirm button (1s fill sweep, release early cancels), last-packet age + queue depth
- `src/command_channel.cpp` — pure SET_RECORDING resend/timeout state machine (no Arduino/LVGL/radio includes); `tick(now_ms, echoed_state)` returns what to send; resends 1/s while pending, 10s timeout. Unit-tested in `test/test_native/`.
- `src/event_queue.cpp` — pure store-and-forward queue for mode events (issue #139): seq assignment (persistent, never reused), resend-all-unacked 1/s, trim on the boat's contiguous-ack frontier (`moana::eventSeq*` helpers in `shared/espnow_protocol.h`). `oldestUnackedSeq()` is the queue's head and rides in every packet as `oldest_unacked_seq` (issue #177) — the boat's only way to tell a gap that will fill from one it must step over, which is what makes the drop-oldest-when-full policy survivable rather than a permanent stall. Persists through a `Store` port; unit-tested in `test/test_native/`.
- `src/alerts.cpp` — fault alerts (issue #162): pure state machine turning link/fix state into cues, each played as a haptic and a tone together. Armed only by the last-known ACTIVE recording echo, so a watch on the charger beside a switched-off boat stays silent; link loss outranks fix loss (out of range, `fix_valid` is frozen, so the fix debounce restarts on recovery rather than counting time nobody was listening); a fix must be gone `kGpsLostMs` continuously because the boat calls its own fix stale after 3s of no GPS event and it flickers under a marginal sky; re-cues every 60s capped at 5 reminders so a boat left off overnight doesn't buzz all night. Ticked in ui.cpp *before* the sleep gate — the point is to reach a wrist that isn't watching the screen — and deliberately does not wake the panel. Unit-tested in `test/test_native/`.
- `src/event_store_nvs.cpp` — production `event_queue::Store` adapter on NVS (atomic blob commits; the watch FS is FAT, which isn't power-fail safe)
- `src/timebase.cpp` — UTC for the clock and for event timestamps: a RAM reference (last known UTC + millis delta, 0 = unknown) in front of the hardware RTC (#144). The RTC is read exactly once, in `begin()`, and written when a telemetry packet shows it has drifted past `kDriftThresholdSeconds` — or when the last write came back refused, which is the only thing that can ask for a retry, since the drift check compares telemetry against the RAM estimate that the same packet rebases — `now()` runs on every 250ms tick and every mode press, and the I2C bus carries the PMU, touch controller and haptic driver with nothing arbitrating it. A time below `kPlausibleEpoch` coming back from the chip is treated as nothing at all: a half-reset PCF85063 reads out around 2000-01-01 and showing that is worse than showing `--:--`. Pure logic behind a `Clock` port; unit-tested in `test/test_native/`
- `src/rtc_clock.cpp` — production `timebase::Clock` on the PCF85063 (`instance.rtc`). `readUtc()` gates on `isClockIntegrityGuaranteed()` — the oscillator-stop bit, set whenever the RTC's rail has been down and cleared on the next write, which is exactly the "has this ever been set, and has it been running since?" question. **The RTC holds UTC**, never local time; conversion is `civil_time`'s, not `mktime`'s, so the C library's timezone state never enters into it. `setDateTime` returns void, so `writeUtc` reads the registers straight back and compares (one second of tolerance, for the RTC's own tick between the two) rather than reporting a success it cannot see. A `false` there is what gets the write retried on the next packet — nothing else would, because after a write the RAM estimate and telemetry never disagree again
- `src/nz_time.cpp` — the NZ daylight-saving rule (#175), applied at render time: NZDT from the last Sunday of September to the first Sunday of April. Both transitions are 02:00 *standard* time, which is the same instant in UTC at either end (14:00 UTC on the Saturday before), so the rule is two date computations and a comparison. It replaced a fixed `12 * 3600`, which was right through the winter and an hour behind for the whole sailing season. The one place on either firmware that renders a local time — the device records UTC and the web app renders in the browser's zone
- `src/civil_time.h` — header-only proleptic-Gregorian date arithmetic (Hinnant's `days_from_civil`/`civil_from_days`). Exists because both of the above need calendar fields from an epoch and neither can use `gmtime`/`mktime`: those read the C library's timezone state, which is whatever the IDF defaults to on the target and whatever the host has in the native test build
- `src/inputs.cpp` — GPIO0 single/double/long press classifier (debounce 30ms, double gap 300ms, long 600ms) + PWR crown click (AXP2101 PKEY IRQ → LilyGoLib POWER_EVENT, dispatched by `instance.loop()`) + DRV2605 haptics (single library effects for the mode vocabulary, and multi-slot sequences — effects interleaved with `hapticWaitMs()` pauses, played by the chip's own sequencer — for the fault alerts that have to be felt rather than merely noticed), polled from `loop()` (the 250ms tick is too coarse); meaning of presses is wired in ui.cpp. Long press reserved for POI (#140); PWR click = manual leg cut (#142).
- `src/buzzer.cpp` — the audible half of the fault alerts: square-wave tones on the PCM amplifier (`instance.player`, compiled in by the variant's `USING_PCM_AMPLIFIER` and initialised by `instance.begin()`). **The only FreeRTOS task in this firmware**, and it earns it: `Player::write()` blocks on the I2S DMA queue until the samples drain, so synthesising a two-second pattern on the loop task would stall LVGL, the button poll and the ESP-NOW handoff for two seconds. The task touches I2S and nothing else — the speaker rail is switched over I2C from `tick()` on the loop task, since the same bus carries the PMU, touch controller and haptic driver with nothing arbitrating it. The rail is parked off at boot (LilyGoLib powers it up in `begin()`) and only raised around a pattern, same reasoning as the GNSS
- `src/sleep_policy.cpp` — 60s screen-off / touch-wake policy, extracted from the UI timer; `noteActivity()` lets button presses wake the screen. `begin()` installs the wake-touch gate (issue #159): the touch controller stays powered through `sleepDisplay()` and LVGL never learns the panel went dark, so a wake stroke would otherwise land as a real press — a tap clicking through, a swipe paging the carousel. Guarding each control can't fix the swipe (the tileview claims the pan as a scroll before any screen sees a gesture), so the stroke is swallowed in the input device's `read_cb` instead, which reports RELEASED upward and calls `lv_display_trigger_activity()` by hand to keep the wake working
- `src/espnow_link.cpp` — raw ESP-NOW I/O: receives `moana::Telemetry`, sends `moana::Command` and `moana::Event`. Validates `version` off byte 0 **before** the length check — a bump can move the length as well as the contents, so checking size first would throw a mismatched boat away as a stray frame — and counts what it rejects **per reason** — version mismatch, foreign type, unreadable length — since `packet_count` only counts frames that passed and a silent rejection looks exactly like a dead boat (issue #173). The version gate itself is `moana::checkFrameVersion` in the shared header, so this end and the boat's run the same rule rather than two copies of it. `Stats::protocolMismatchFresh()` answers whether a rejection is recent enough to still mean "the boat is there and unreadable"; `ui.cpp` adds only the link state
- `src/fonts.h` + `src/font_speed_170.c`, `src/font_time_56.c`, `src/font_ui_{24,28,40}.c` — generated Montserrat-Medium fonts with **tabular figures frozen in**; `font_speed_170` is digits-only (`0-9.-`) and `font_time_56` near enough (`0-9:-`), the `font_ui_*` set is ASCII and replaces LVGL's built-in `lv_font_montserrat_*`. Narrow ranges are the reason the big sizes are affordable at all — full ASCII at 56px is ~330KB of source against 42KB for the glyphs a clock actually draws. The flip side: a character outside a font's range draws as a hollow box, not as nothing, so any label reaching past ASCII needs its codepoint added to that size's range in `build.sh` and the font regenerated. `font_ui_24` carries U+2022 for the Stats session line; nothing else on either firmware draws a non-ASCII character. The built-ins are the same typeface but proportional (`'1'` ≈ half the advance of `'0'`), so every digit change reflowed the SOG readout and the stats grid. Regenerate all four — and the device's matching VLW set — with `tools/fonts/build.sh`; see `tools/fonts/README.md` for why the feature has to be frozen into the TTF rather than requested at render time.

### Tests

`pio test -e native` — googletest over the pure modules (command channel, event queue, stats engine, timebase, NZ time, alerts), mirroring `device/`'s native recipe. Keep decision logic out of radio/UI code so it stays testable here.

### Rounded corners

The glass corners hide pixels LVGL thinks it owns (LilyGoLib passes the raw panel resolution straight through) — measured at ~70px. All content is centre-anchored to sidestep the arcs: the header items cluster around the horizontal centre (offsets in `src/header.cpp`), and each tile's content sits in the full-width middle band, which needs no inset at all. Don't pad the root — that caps the middle band for no reason.

### Display sleep

The panel sleeps after `kScreenOffMs` idle (LVGL input inactivity) and any touch wakes it; the policy lives in `src/sleep_policy.cpp`, called first in the UI refresh tick. The waking stroke only wakes — see the wake-touch gate above. After `kSleepHomeMs` (30s) dark the carousel returns to Speed, timed from the screen going off rather than from the wake, so the homing happens while the panel is still dark and a wake opens on Speed instead of flicking to it. With nothing recording, home is Control instead, so the first glance lands on Start (issue #184). Deliberately `sleepDisplay()` (~10mA, touch controller stays awake) and not `instance.lightSleep()`: light sleep saves much more current but drops the WiFi radio, so ESP-NOW telemetry stops, and it doesn't re-init WiFi/ESP-NOW on wake.

Key LilyGoLib APIs: `instance.begin()`, `beginLvglHelper(instance)`, `instance.pmu` (AXP2101/XPowersLib), `instance.sleepDisplay()`/`wakeupDisplay()`, `instance.powerControl(POWER_GPS, false)`.

## On-water checklist

Sender: either the main CoreS3 firmware (`cd ../device && pio run --target upload` — telemetry is always on) or the standalone `espnow-sketch` env.

1. Flash; readout shows grey `--` and a greyed link icon with a red slash through it until the first packet arrives. The **clock** is the exception — since #144 it reads off the RTC, so it shows the right local time immediately on any watch that has ever had a link, and `--:--` only on one that never has
2. With the sender running: digits track SOG at 1Hz, the link arcs turn white, the clock above the digits is sane in **local** time (`src/nz_time.cpp` owns the NZST/NZDT rule) and shows on the Speed tile only
3. Kill the sender: link arcs go amber at 3s (`kLinkFreshMs`), grey with a red slash at 10s (`kLinkLostMs`), digits grey out but keep the last value
   - Protocol mismatch (#173), the state this one is easily confused with: reflash the boat only after bumping `kProtocolVersion` in `shared/espnow_protocol.h` and leave the watch on the old build. Within 10s the arcs must go **amber with the slash** — not grey — and a second header line must read `RX v<n> WANT v<n+1>`. Reflash the watch and it clears on the next packet. Grey-and-slashed with no second line means silence; amber-and-slashed means the boat is right there and the flash is half-finished
4. Screen blanks after 60s untouched (`kScreenOffMs`); a tap wakes it; packet counter keeps climbing across the sleep (check serial, or watch the link arcs stay white on wake)
5. Battery %: sane, and "+" appears when charging over USB
6. Carousel wraps both ways: from Speed, swipe left → Mode → Control → Stats → back to Speed; swipe right from Speed lands straight on Stats
7. Mode tile: tap ANCHOR — haptic fires, the carousel returns to Speed, and the chip flips to ANCHOR only once the boat echoes it. After a sync, that mode must appear as a segment in the web UI
8. Tap to wake a dark screen while the Mode tile is showing: must NOT set a mode (the wake tap is swallowed)
9. *Swipe* to wake a dark screen: the panel lights and the carousel does NOT move, even if the finger keeps travelling after the screen comes on
10. Leave the screen dark 30s+ on any tile, then wake: it opens on Speed, already there, with no visible slide from the old tile. Wake inside 30s and the tile you left is still showing
    - Not recording (#184): Speed digits are amber and the chip reads `NOT RECORDING`; start recording and they turn white and the chip shows the mode. Not recording, a wake after 30s+ dark opens on Control; recording, it opens on Speed as before
11. Stats tile: swipe down to a past leg, swipe away to another tile, swipe back — it shows the current leg again. Wake from a short sleep with a past leg on screen and it stays put
12. Mis-press debounce (#161), recording: tap SAIL then MOTOR a few seconds later — the Stats tile must still show ONE leg, now labelled MOTOR, keeping its number and its elapsed time; the mode chip on Speed follows the echo to MOTOR as usual. Wait out `kMinLegMs` (20s) between the two taps instead and it must cut a new leg normally. After a sync, the web UI shows one MOTOR segment starting at the *first* tap
13. Fault alerts (#162), all of which need recording ACTIVE first — nothing below buzzes while idle:
    - Not recording, kill the sender: no buzz, ever (the charger case)
    - Recording, then kill the sender: at 10s, a ~3s burst of smooth haptic alerts *and* three long tones, repeating each minute (`kRepeatMs`), five reminders then quiet (`kMaxRepeats`). Sender back → two light clicks, silently. It must fire with the screen dark, and must NOT light the panel
    - Recording, take the boat's GPS under cover (or unplug the antenna): a ~3s burst of *rough* buzzes and a warbling two-tone ~10s after `fix_valid` drops, not on the first flicker; fix back → the same silent clicks. The two faults are told apart by texture rather than by counting, so feel and hear them back to back at least once
    - Recovery is felt and never heard — no tone on the way back from either fault
    - Tones must not stutter the UI: swipe the carousel through a whole alert and it stays smooth, and the packet counter keeps climbing across it
    - With the boat's GPS already lost, start recording: the fix alert is immediate, not 10s later
14. Clock off the RTC (#144/#175):
    - With the sender running and a GPS fix, note the time; kill the sender, reboot the watch, leave the boat off. The clock must come back showing the right time within a second of boot, before any packet — this is the anchor-at-night case the whole slice exists for
    - Leave it running boat-off for an hour: the clock keeps ticking and stays within a few seconds. Bring the boat back and it re-disciplines silently, with no visible jump
    - Serial must be quiet on the I2C front while the clock is right — the RTC is written on drift, not per packet (`kDriftThresholdSeconds`). A write every second is the bug this threshold exists to prevent. A write that is *refused* is the exception: it retries every packet until the chip takes it, which is the point
    - DST is a calendar rule, not something the water can test: check it against `pio test -e native` (`test_nz_time.cpp`) and, on the day, that the watch reads the same as a phone on the last Sunday of September and the first Sunday of April
